Context

The Problem & The Approach

⚠️ The naïve flow — and why it breaks

request ──► vendor call ──► Kafka publish ──► 200 OK
        (everything on the request thread)
  • Event loss — if Kafka is down, the publish is lost silently.
  • Service stalls — under load the producer buffer fills and request threads block.
  • Duplicate SMS — a retry re-runs the vendor call, messaging the user twice.
  • Coupling — the sender fails whenever the store is slow or down.

✅ The principle: decouple acceptance from work

request ──► durable outbox write ──► 202 Accepted
        background worker does the real work later
  • The request path does only a fast local DB write — never blocks on Kafka/vendor.
  • A downstream outage just makes rows queue, then drain on recovery.
  • A two-step state machine + idempotency keys make delivery exactly-once.
  • Stuck messages are dead-lettered and replayable — never lost, never infinite.

The Centerpiece

The Transactional Outbox

   ┌─────────┐  vendor call   ┌──────┐  publish to Kafka   ┌───────────┐
   │ PENDING │ ─────────────► │ SENT │ ─────────────────► │ PUBLISHED │
   └─────────┘                └──────┘                     └───────────┘
        │ vendor keeps failing  │ publish keeps failing
        └──────────────► after max-attempts (10) ──────► ┌────────┐
                  with exponential backoff               │ FAILED │ replayable
                                                          └────────┘

🛡️ Why two steps

Splitting "call the vendor" (PENDING→SENT) from "publish the event" (SENT→PUBLISHED) is the no-duplicate-SMS guarantee. Once a row is SENT, a Kafka failure only retries the publish — the vendor is never called again.

⏱️ Backoff & dead-letter

Each failure doubles the delay (2s→4s→8s … capped 5 min) via a future nextAttemptAt. The ~13-min window rides out a transient outage instead of quarantining good messages; only a genuinely stuck row hits FAILED.

Behaviour

End-to-End Flow & Idempotency

🟢 Happy path (send → stored)

1  POST /v1/sms/send
2  SISMEMBER blocked_users → ok
3  INSERT outbox PENDING
4  return 202 {messageId}      ≈ ms
5  worker: vendor.send → SENT
6  worker: publish     → PUBLISHED
7  Go: consume → upsert(eventId)
8  Mongo: 1 document
9  UI History → visible

🔗 The idempotency chain

Vendor side:  key = outbox row id
   replay → cached result → SMS once
Storage side: eventId = row id
   redelivery → upsert → 1 doc

✅ Net guarantee

Exactly-once to the recipient and exactly-once in storage — even though Kafka in the middle is at-least-once by design. The two ends are idempotent, so duplicates in the stream are harmless.

My Workings · Hardening

Failure Modes — Found & Fixed

Each was discovered by stress-testing the pipeline (kill Kafka, crash mid-step, redeliver) and closed with a concrete change.

Failure modeResolutionStatus
Event lost when Kafka is down (fire-and-forget on request thread)Outbox pattern — durable H2 queue + async worker; request path never blocks on KafkaFIXED
Duplicate SMS on retry / worker crashTwo-step state machine + idempotency key passed to the vendorFIXED
Duplicate events in MongoDB (at-least-once delivery)Consumer upsert keyed by eventId + sparse unique indexFIXED
Poison messages retry foreverExponential backoff + dead-letter (FAILED) + admin replay endpointFIXED
Open admin endpoints (anyone could block / replay)API-key filter on the admin surface + gateway key injectionFIXED

Live-validated: during testing, a Kafka restart produced 3 duplicate Mongo rows — exactly the predicted at-least-once behaviour — which the eventId upsert then collapsed back to one. The diagnosis and the fix matched.

🎯 The thread

Start simple, then systematically stress-test: what if Kafka dies? what if the worker crashes mid-step? what if a message is redelivered? Each question exposed a real failure mode and led to a concrete fix.

✅ Where it stands

The outbox foundation, the end-to-end idempotency chain, and the public/admin split are production-shaped. The open items are scaling and multi-tenancy — the next layer, not dead-ends.
