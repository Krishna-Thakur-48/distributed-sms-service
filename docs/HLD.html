1. Introduction & Overview

The Distributed SMS Service is a polyglot, event-driven platform that accepts SMS-send requests, delivers them to a vendor, and durably records every outcome. It is composed of two independently deployable microservices that never call each other directly — they communicate asynchronously through a Kafka topic.

The central design principle is decoupling acceptance from work: a request is durably accepted and acknowledged in milliseconds, while the actual vendor call and event publication happen in the background. This makes the system resilient to downstream outages and guarantees that each recipient is messaged exactly once.

2. Goals & Non-Goals

2.1 Goals

  • Durable acceptance — once a request returns 202 Accepted, it will never be lost.
  • Exactly-once to the recipient — a retry or crash must never send the same SMS twice.
  • Exactly-once storage — the history store must hold one record per request regardless of redelivery.
  • Resilience to outages — a Kafka or store outage must not bring down the request path.
  • Operability — stuck messages are quarantined and replayable, not lost or infinitely retried.
  • Protected admin surface — privileged operations require authentication.

2.2 Non-Goals (for this iteration)

  • Real vendor integration (a deterministic mock vendor stands in).
  • Multi-tenancy / per-seller isolation (single-operator model for now).
  • High-availability infrastructure (single-broker Kafka, single-node stores).
  • User-facing authentication (admin uses a shared API key; see §14).

3.1 Why two services

The sender is synchronous and user-facing — it must respond fast and stay available. The store is asynchronous and write-heavy — it processes at its own pace. Splitting them lets each scale and fail independently. Kafka is the durable buffer between them, so the sender never blocks on, or fails because of, the store.

5. End-to-End Data Flow

5.1 Happy path (send → stored)

 1. Client → POST /v1/sms/send {phoneNumber, message}
 2. Sender: SISMEMBER blocked_users → not blocked
 3. Sender: INSERT outbox row (status=PENDING, id=UUID)
 4. Sender: return 202 Accepted {status:"ACCEPTED", messageId:UUID}      ◄── fast, durable
 5. Worker (≤1s later): PENDING row → vendor.send(id, phone, msg) → SUCCESS
 6. Worker: UPDATE row status=SENT, vendorMessageId, attempts=0
 7. Worker (same tick): SENT row → publish to Kafka (blocking, 5s ack)
 8. Worker: UPDATE row status=PUBLISHED
 9. Go: ReadMessage → unmarshal SmsEvent
10. Go: ReplaceOne(filter={eventId}, upsert=true) → MongoDB
11. UI History: GET /v1/user/{phone}/messages → event visible

5.2 Blocked path

 1. Client → POST /v1/sms/send
 2. Sender: SISMEMBER blocked_users → BLOCKED
 3. Sender: throw BlockedUserException → 403 Forbidden     ◄── no outbox row, no SMS

6. The Outbox Pattern

The outbox is the heart of the design. Rather than calling the vendor and publishing to Kafka on the request thread, the sender writes a durable row to a local relational table and returns. A background worker then drives that row through a state machine.

6.1 State machine

   ┌─────────┐   vendor call    ┌──────┐   publish to Kafka   ┌───────────┐
   │ PENDING │ ───────────────► │ SENT │ ───────────────────► │ PUBLISHED │ (terminal)
   └─────────┘                  └──────┘                      └───────────┘
        │                           │
        │ vendor keeps failing      │ publish keeps failing
        ▼                           ▼
   (backoff retry)            (backoff retry)
        │                           │
        └───────────► after max-attempts ──────────► ┌────────┐
                                                      │ FAILED │ (dead-letter, replayable)
                                                      └────────┘

6.2 Why two steps

Splitting "call the vendor" (PENDING→SENT) from "publish the event" (SENT→PUBLISHED) is what guarantees no duplicate SMS. Once a row is SENT, a Kafka failure only ever retries the publish step — the vendor is never contacted again.

6.3 Backoff & dead-letter

Each failure doubles the retry delay (2s → 4s → 8s … capped at 5 min) by stamping a future nextAttemptAt; the worker only picks up rows whose backoff has elapsed. After max-attempts (10) the row becomes FAILED and the worker stops touching it. The long backoff window (~13 min of continuous failure) means a transient Kafka outage is ridden out rather than wrongly quarantined.

Key property: the request thread does only a fast local DB write. A Kafka or vendor outage causes rows to queue in H2 — the service stays responsive and drains automatically on recovery.

7. Reliability & Idempotency

The system was stress-tested against concrete failure modes. Each exposed a real problem and a fix.

Failure modeResolutionStatus
Event lost when Kafka is down (fire-and-forget on request thread)Outbox pattern — durable H2 queue + async worker; service never blocks on KafkaFIXED
Duplicate SMS on worker crash/retryTwo-step state machine + idempotency key passed to the vendorFIXED
Duplicate events in MongoDB (at-least-once delivery)Consumer upsert keyed by eventId + sparse unique indexFIXED
Poison messages retry foreverExponential backoff + dead-letter (FAILED) + admin replayFIXED
Open admin endpointsAPI-key filter + gateway injectionFIXED

7.1 The idempotency chain

  Vendor side:    idempotency key = outbox row id
                  → vendor returns cached result on replay → recipient messaged ONCE

  Storage side:   eventId = outbox row id (carried in the Kafka event)
                  → consumer upserts on eventId → MongoDB converges to ONE document

  Net guarantee:  exactly-once to the recipient AND exactly-once in storage,
                  even though Kafka in the middle is at-least-once by design.
The crash window: the vendor call and the SENT write are not atomic. If the worker crashes between them, the row is still PENDING and the vendor would be called again on restart — which is exactly why the idempotency key exists: the vendor dedups on it, so even that window cannot double-send.

9. Security

Admin endpoints (/v1/sms/block/** and /v1/sms/outbox/**) require an X-API-Key header validated by a Spring OncePerRequestFilter. Missing or invalid → 401. Public endpoints (/send, /health) are open. 

  Browser (no secret) ──► Proxy/Gateway (holds key, injects X-API-Key) ──► Java filter ──► ✅
  Attacker ───────────────────────────────────────────────────────────► Java filter ──► ❌ 401

The secret lives only in the gateway, never in browser code. This is correct for an internal operator; the production path is per-seller keys or JWT/OAuth2 with roles (see §14).

13. Deployment

13.1 Demo topology

Infrastructure (Kafka, Zookeeper, MongoDB, Redis) runs via docker-compose. The Java and Go services and the proxy run directly so logs and restarts are visible during the demo.

13.2 Production topology

  • All components containerized (services include their own runtime via multi-stage Dockerfiles).
  • Services address dependencies by container/DNS name, not localhost.
  • Orchestrated by Kubernetes for auto-restart, horizontal scaling, and zero-downtime rolling deploys.
  • Kafka: 3 brokers, 3 replicas, multiple partitions, acks=all + idempotent producer.
  • H2 → managed Postgres; secrets via a secret manager, not config files.

15. Appendix & Glossary

TermMeaning
Outbox patternPersist intent to a local table first, then process asynchronously, so acceptance is decoupled from work and nothing is lost.
Idempotency keyA stable per-request id ensuring a repeated operation has the same effect as doing it once.
At-least-once deliveryKafka's guarantee that a message is delivered one or more times — consumers must be idempotent.
Dead-letterA terminal FAILED state for messages that exhaust retries, set aside for inspection/replay.
Consumer groupA named set of consumers sharing a topic's partitions and tracking processed offsets together.
BackoffIncreasing the delay between retries to ride out transient outages.
Summary. A two-service, event-driven SMS platform whose transactional outbox makes acceptance durable and decoupled, whose end-to-end idempotency chain guarantees exactly-once delivery to both the recipient and the store, and whose dead-letter queue and API-key gate make it operable and protected. The remaining work is scaling and multi-tenancy — the foundation is sound.
